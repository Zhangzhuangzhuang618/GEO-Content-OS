## 1. 目标与边界

首版仅限 **官网、列举网、抖音**，这三个平台的每个账号都可独立配置以下内容：

1. 账号默认生文风格：**现有常规风格 / 硬广·多公司推荐**。
2. 推荐企业名单：可增删、排序，每家绑定明确的资料来源。
3. 已有日批策略可单独切换这两种风格，也可跟随账号默认值。
4. 手动生文、显式重新生成时，可为所选目标账号单次指定风格。

首期仅做两个内置风格，不做自由提示词模板编辑器、混合比例、按星期轮换、跨账号一键批量修改或新的自动发布平台接入。

当前 Contracts 声明 9 个平台，现有日批调度覆盖官网、百家号、搜狐号、列举网、抖音；这是现状，不是首版改造范围。

- 纳入：官网、列举网、抖音的账号配置、日批、手动生文、质检、配图及既有发布链路。
- 明确排除：百家号、搜狐号、小红书、知乎、微信公众号；头条号也不在“首版只改三个平台”的范围内。
- 用户后续补充：百家号只做既有“内容来源”配置切换，改为独立生成，不再新增官网派生；仍不参加硬广风格改造。
- 不给排除的平台新增风格 UI、配置 API 能力、日批选项、私有引用支持或新的发布能力。
- 公共代码可以为这三个平台增加受控分支，但其他平台仍走原逻辑，并须通过无行为变化的回归测试。

初始推荐企业候选：

- 广东众人搬家起重吊装有限公司
- 广州志远搬家服务有限公司

以上只是用户指定的名单，不等于已确认它们的服务能力或资料完备。不得在数据库迁移中将两家名称写为全租户白名单，也不自动给全部账号启用硬广。

## 3. 使用规则与界面

### 3.1 配置层级

| 入口 | 可选内容 | 生效范围 |
| --- | --- | --- |
| 官网/列举网/抖音账号的“内容设置” | 账号默认：常规 / 硬广；推荐企业及顺序、资料绑定 | 后续未显式覆盖的生成任务 |
| 官网/列举网/抖音日批设置 | 跟随账号 / 常规 / 硬广 | 此后新建的日批尝试，页面显示实际生效风格 |
| 已允许的“保留历史并重新发起”确认框 | 使用日批设置 / 本次常规 / 本次硬广 | 新建的这一轮尝试；不修改长期设置 |
| 手动生成或显式重新生成 | 三个范围内平台选择目标账号；跟随账号 / 本次常规 / 本次硬广 | 本次所选账号对应的内容变体；其他平台保持旧入口 |

解析顺序：

- 日批：**本次重开指定值 → 日批设置 → 账号默认 → 常规**。
- 手动：**本次指定值 → 账号默认 → 常规**。
- 自动局部修复、质检重写、网络重试：保持原任务冻结值，不重新读取账号默认值。

单次指定只切风格；推荐名单沿用所选账号的配置，不增加另一套单次企业名单编辑器。

### 3.2 日批切换的时间边界

- 今天尚未创建批次：保存日批风格后，按既有触发时间创建的批次采用新设置。
- 已创建、运行中或已排期：显示“当前批次风格”和“后续批次风格”，保存新设置不改本次候选、正文或排期。
- 满足既有重开条件：用户可以为下一 `attempt_no` 选择另一种风格，只补当天缺口，不替换原来占用名额的内容。
- 因资料缺失而原地重试：保持原风格和名单；补齐资料后恢复，不把“重试”偷换成换模板。
- 不新增强制终止正在运行批次的能力，不绕过各平台既有取消/重开限制。旧发布失败任务不自动替换、补发。
- 首期不支持同一批次按比例混用两种风格；同一天不同尝试可以不同，历史页面标明各自风格。

这意味着“日批可切换”是可配置的实际生文风格，不仅是手动生文选项；同时不是对正在执行的整批文章原地换模板。

### 3.3 口吻与硬广的关系

- 常规风格：完整保留现有抖音企业官方、一线师傅和客户口吻的行为。
- 硬广风格：本次使用企业介绍口径，不执行客户尚未成交的固定首尾句或师傅单一雇主结尾；界面明确显示这一点。
- 不修改账号原本保存的口吻，切回常规后恢复原口吻。真实身份、案例、评价不得编造的规则继续适用。
- 本次不将抖音三种口吻扩展成其他平台的新功能；三个范围内平台共用的是“风格”和“推荐名单”。

## 4. 企业资料与授权边界

为简化首期实现，推荐名单直接按账号保存，不新增全局企业库或跨工作区资料共享系统。

每个条目包含稳定条目 ID、法定企业全称、绑定的资料 ID；数组顺序即推荐顺序。建议硬广每篇选择 **2–6 家**，初期两家都选用；不随机抽样、不生成排名。

- 名称来自配置，不由模型猜测；两家公司就写两家，标题不得凑“六家”。本期不自动生成企业简称。
- 可保存尚未补齐资料的名单草稿；进入硬广生成前必须逐家检查有效资料和适用范围。缺哪家、缺什么在管理界面说明，不能先消耗模型额度再发现资料为空。
- 查询必须同时约束租户、账号工作区、当前项目或工作区公共资料、文档/分块有效状态、有效期与删除状态。客户端传入资料 ID 不等于取得访问权限。
- 若众人和志远的资料分属不同工作区，首期需将经授权的资料通过现有上传功能放入使用该推荐名单的工作区；不能仅因两家都属于用户就绕过隔离读取。实际资料所在位置留待获准实施后只读核对。
- 同一份资料绑定到企业只是检索边界，不等于其中每句话都证明该企业能力。推荐理由须逐条核对主体、场景、地区、条件和引用，禁止把 A 的资质或服务承诺写给 B。
- “保价、费用封顶、无损拆装、免费服务、持证作业、赔付”等具体承诺仅在对应企业资料直接支持时输出。用户示例只借用组织方式，不视为众人/志远的事实资料。
- 不将推荐名单并入 `brand_profiles.positioning/cta`；当前发布企业身份、官网联系号码、列举网发布主体和当前企业证照仍分别保留。
- 推荐企业引用默认只作内部事实依据；资料 ID、私有地址不进入正文或导出。首期不增加推荐企业证照原图自动展示，本企业既有授权证照能力保持。

## 5. 硬广模板及平台适配

### 5.1 公共内容结构

1. 场景与痛点：围绕当篇地区、服务、搜索主题写正常开篇，不照抄示例，不虚构城市细节或消费者案例。
2. 企业推荐：按名单逐家生成“完整名称 + 资料支持的服务/适用场景 + 具体选择理由”；可以写差异，但不强行捏造差异或排名。
3. 收尾：给出预约前需核对的事项，再按平台规则生成允许的咨询引导。

使用独立的浅层推荐草稿结构，例如 `opening`、`recommendations[]`、`closing`、`evidence_claims`；由服务端组装现有内容文档及平台字段。首期不改成开放式模板解释器，也不要求所有平台字数、段落数量完全一致。

### 5.2 抖音

- 保留当前标题、主文案与话题总长度、图片数量等发布格式边界：现有代码为标题 6–20 字、主文案 420–900 字、主文案与话题合计不超过 1000 字、6–9 张卡片。
- 以两家公司为例：封面、场景痛点、众人介绍、志远介绍、预约核对、总结，共 6 张；企业数量增加时最多 9 张。
- 法定名称较长时放正文/卡片正文，卡片标题写服务场景，不强塞进较短标题槽位，不自行起简称。
- 新增硬广分支的企业覆盖、顺序、引用主体和重复检查；不对常规风格全局取消“本企业次数、客户结尾、师傅身份”规则。
- 现有“方案/报价/防护/排期”固定语义槽位不再强套硬广草稿；必要信息根据选题自然进入开篇、推荐理由或收尾。
- 章节、企业推荐与对应卡片建立稳定映射，局部修复只改命中企业/段落；无事实支持时不得为凑齐卡片补造承诺。正文编号是展示顺序，不标为榜单。

### 5.3 官网、列举网及排除平台的边界

- 官网：允许当前版本中授权的推荐名称；网站发布者、Schema.org 作者/组织、服务号码及资质归属仍是当前企业，不能替换成两家混合身份。
- 列举网：在正文规则允许范围内适配推荐段落，维持发布主体、联系方式及禁止宣传词限制；风格开关不豁免联系方式或事实门禁。
- 百家号：使用已有独立生成能力，将目标生产策略设为 `source_mode=independent`、`independent_fallback_enabled=false`；不新增硬广支持、不删除历史派生代码，不扩大全局企业白名单。
- 切换保持启停状态、开始时间、篇数、候选上限、排期与质量阈值。独立生成不依赖官网发布结果，也不是仅在官网供稿不足时补量。
- 只阻止新官网事件创建派生任务；已经创建的派生运行保留原来源模式，不能批量改写为独立生成。是否取消这类在途任务需另行明确，不自动重跑、删除或补发。
- 搜狐号、头条、知乎、小红书、公众号保持现有生成、质检、Render 和交付行为。共享代码测试需验证它们不会继承本次新增的名称允许范围。
- 抖音继续使用已上线的有效私有引用机制；其他平台私有引用功能不纳入本期。

## 6. 建议的数据与契约改动

以下为建议命名，实施前按当前迁移编号与仓库规范确定，不提前占用迁移编号。

### 6.1 一个账号内容策略表

新增 `platform_account_content_policies`，包含：

- `tenant_id`、`workspace_id`、`account_id`，每账号最多一条；复合外键和服务端查询同时校验所属关系，明确限制账号平台为官网/列举网/抖音。
- `default_style`：`standard` / `company_recommendation`，默认 `standard`。
- `recommended_companies_json`：上述有界、严格校验的有序条目；默认空列表。
- `version`、创建/更新人、时间及审计信息；独立于平台凭证与能力探测。

不复用 `capabilities_json` 存用户设置，避免账号探测/刷新覆盖内容策略。

### 6.2 扩展现有记录

- 官网及浏览器两类日批策略表增加可空 `content_style_override`：空表示跟随账号，另外两值分别为常规/硬广；浏览器表的搜狐号行不允许设置新覆盖值。百家号表不修改。
- 官网及浏览器两类日批表增加 `editorial_policy_snapshot_json`：范围内平台创建尝试时在事务内解析并冻结风格、账号、策略版本、名单顺序、资料绑定、模板版本；搜狐号不创建新风格快照。百家号批次表不修改。
- `content_versions` 增加服务端专用 `editorial_context_json`：记录本变体的生效风格、目标账号、名单和解析后的证据绑定、上下文哈希；与正文一同插入，保持不可变。
- Writer Input、相关运行输入哈希/幂等指纹包含解析后的上下文；同包不同平台分别持有上下文，不使用全局共同白名单。
- 老批次/老内容没有新上下文时按旧规则处理，不根据今天的账号设置把历史内容解释成硬广；不回填历史正文、引用、质量报告或排期。
- 批次冻结配置和资料绑定，不冻结永久有效性。候选生成及发布时资料若失效，明确停止，不擅自替换来源；补资料如需改变名单绑定，走后续新尝试。

### 6.3 API 与前端

- 新增账号内容策略 GET/PUT，仅接受官网/列举网/抖音；沿用既有发布管理权限，并核对资料访问权限；写入带版本、幂等和审计。排除平台返回不支持，不仅依赖前端隐藏。
- 官网及浏览器日批契约扩展风格覆盖字段；范围内平台已有重开接口可选单次风格，返回新尝试的实际快照摘要。复用浏览器/重开 Schema 的搜狐号和百家号服务端必须拒绝新参数，不改变其行为。
- 手动生成请求仅对三个范围内平台开放目标账号和风格覆盖；服务端拒绝客户端自造的“已验证企业/引用快照”。不允许在同一次多平台内容包里隐式扇出同一平台多个账号，需分别发起。
- 多账号平台必须明确选一个账号；唯一账号可自动选中。`GenerationRequestService` 与 Writer Input 构建使用同一解析结果，不能一处选账号、另一处重新要求全平台只有一个账号。
- 未选账号的既有通用生成入口仅保留常规行为，不能使用账号推荐名单；生产账号定向生成按现有强制账号配置执行。
- 仅三个范围内平台账号展示公共“内容设置”；官网与浏览器日批面板复用小型风格控件，搜狐号分支不展示。内容预览/批次详情展示实际风格和名单，不只展示实时默认值。
- 同步 Contracts、Web Schema、OpenAPI、事件/技能输入契约与示例测试。

## 7. 贯穿全链路的实现要求

### 7.1 风格与企业允许范围

公共纯函数解析风格及企业范围，必须显式接收目标平台和账号并校验范围；数据库读取分别由 API/Worker 现有数据层完成，不引入通用工作流引擎。

- 常规：只采用原有当前企业策略。
- 硬广：当前发布企业身份保持独立；新增“本次授权推荐企业”集合，并约束到推荐内容和对应证据。
- 非官网/列举网/抖音：无论输入、源稿或约束是否包含新字段，都不能启用新风格或扩大企业范围。
- 生成、局部修复、技能输出检查、模型质检、质检结果校验、确定性扫描、Publisher、Render 使用相同版本上下文。
- 质检运行的输入哈希/复用判断包含上下文哈希与模板规则版本，不把同正文在另一种风格下的旧报告直接视为本次质检通过；已保存报告保持不变。
- 核对已发布提示词和平台规则是否包含冲突的旧模板限制；需要更新时创建新版本并按风格适用，不原地改历史规则或降低现有质量分数阈值。
- 不以“内容自己带有某风格字段”作为放行依据；内容 JSON、资料正文和模型返回都无权增加名单。
- 不通过移除质量问题、修改评分、扩大通用白名单、放开所有竞品名称来实现新模板。

### 7.2 重写、人工编辑与发布

- 自动修复保持原快照；用户显式重新生成才可选新风格。风格变化时与旧结构不兼容的锁定段落需提示解除锁定或拒绝请求，不能假装已切换。
- 人工编辑新版本继承原服务端上下文；回滚取回被回滚版本的上下文，不读取账号当前默认名单。
- 同内容哈希命中旧版本时，额外检查上下文是否一致；不同上下文不得静默复用旧版本。首期保留既有内容去重约束，返回“内容无变化但配置不同，需生成新稿”，不覆盖历史版本。
- 发布账号必须匹配内容版本绑定账号；改投账号不能自动获得对方企业名单权限。
- 发布前复核引用有效性与主体对应，不把快照视为对已撤销/删除资料的永久授权。
- 保存新账号名单只影响未来任务；需撤销旧资料使用时走明确资料失效流程，发布检查可据此阻断。不能通过编辑名单悄悄重写已排期文案。
- 保留已部署的官网双电话兼容与抖音私有引用校验，不因本次改动回退。

## 8. 验收与测试计划

本轮未运行业务测试，也未声称这些新增功能已通过验证。实施后至少覆盖：

1. **配置与隔离**：官网/列举网/抖音账号均能保存/回显，其他平台无新入口且 API 拒绝新配置；账号 A 的名单不影响 B；跨租户、跨工作区、跨项目、停用账号、伪造来源 ID 被拒绝；过期版本冲突和重复提交幂等。
2. **风格解析**：常规/硬广/跟随默认；日批显式选择优先于账号默认；手动指定不修改长期配置；两家公司名单顺序一致。
3. **批次一致性**：官网/列举网/抖音都冻结；批次运行中改设置不混风格；新尝试采用新值且保留历史计数；同批重试不漂移；部署前老批次保持常规旧规则；搜狐号/百家号原调度和重开不受影响。
4. **手动多账号**：同平台两个账号可明确选择；缺少选择返回明确提示；Writer Input、变体记录、后续发布账号一致；不同平台变体不共享推荐范围。
5. **事实与名单**：选两家只推荐两家；名单外公司、虚构第六家、张冠李戴资质/赔付、无依据排名、来源缺失或已失效被阻断；不把名称白名单当作事实已核验。
6. **抖音结构**：两家和六家边界、正文及卡片顺序/覆盖、长全称、字数与话题上限、局部修复不删另一家事实；常规三口吻、单企业次数和既有客户口吻回归通过。
7. **跨阶段闭环**：同一真实资料样稿从生成、质检、图片组装到 Publisher/Render dry-run 都通过，不能只测提示词包含新字段。
8. **平台回归**：官网主体/电话/Schema.org 正确；列举网联系方式限制不变；百家号从官网源稿收到新约束也不获得推荐放行；搜狐号、头条、知乎、小红书、公众号的既有样例、名称门禁及私有引用限制保持原结果。
9. **版本与恢复**：自动重写、人工编辑、回滚、同哈希不同上下文、锁定旧结构、换账号、旧队列重放、撤销资料后发布阻断。
10. **生产回归**：原有官网两个电话门禁及抖音私有资料引用测试继续通过，不自动重跑任何历史失败任务。

执行层次：公共策略与 Writer 单元测试 → 契约/迁移/API/数据库集成 → Web 交互测试 → 模拟平台全链路 → 构建、类型、格式与静态发布检查。
之后才在明确授权的账号与有效资料上做有界真实生成，记录实际通过率和原始失败原因；不预先承诺某个模型通过率，不擅自增加重试次数或升级模型消耗。
