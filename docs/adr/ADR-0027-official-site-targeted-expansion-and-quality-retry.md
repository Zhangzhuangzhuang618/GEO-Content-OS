# ADR-0027：官网正文定向补写与质检语义重试

- 状态：已批准实施
- 日期：2026-07-28
- 影响范围：仅 `official_site` 的正文生成与所有平台共用的 Quality Checker 运行时可靠性
- 前置决策：ADR-0013、ADR-0021、ADR-0023、ADR-0025

## 1. 问题

ADR-0025 将官网正文写作目标提高到 1,500–2,200 个有效字符，但生产监控仍出现 1,108、1,273 和 1,277 个有效字符的短稿。原实现发现短稿后要求模型整篇重写，模型可能把已有正文重写得更短；仅调整提示词不能可靠保证模型持续计数。

Quality Checker 还出现结构合法但语义不合法的输出：输入存在高风险且无支持证据的事实，模型却没有返回对应 `BLOCK` 问题。Skill 的服务端断言会正确拒绝该结果，但运行时没有携带明确失败条件重新执行，导致候选直接失败。

## 2. 决策

1. 官网正文继续执行 1,300–2,500 个有效字符硬门槛，不降低任何质量标准。
2. 首稿提示改为正向结构预算：直接回答、至少三个分节、可执行清单或比较项、结论，并以 1,700–2,100 个有效字符为目标。
3. 提示明确说明真实流程后果：正文不足 1,300 个有效字符会被自动发布流程判为敷衍并拒绝。该说明用于提高模型遵循率，但服务端计数仍是唯一判定依据。
4. 首稿只有长度不足时，不再整篇重写。系统保留标题、摘要和全部已有正文块，进入独立补写阶段。
5. 补写阶段每次只返回 2–5 个新的段落或清单块，服务端根据当前有效字符数给出缺口和 1,700 字目标；最多补写两轮。
6. 服务端只追加不重复、非空且不会使正文超过 2,500 个有效字符的块，并生成确定性 `supplement-<round>-<index>` block key。已有正文不被覆盖或截断。
7. 补写引用仍只能使用输入中已存在的 citation ID；未知引用、重复内容、绝对化表述和其他质量问题继续触发失败。
8. 如果首稿除长度外还有标题、结构、重复、引用或事实边界问题，仍先完整修复一次；只有剩余问题全部是长度不足时才进入定向补写。
9. Quality Checker 的 JSON Schema 自动修复保持不变。若最终结构合法但服务端语义断言返回 `SKILL_OUTPUT_INVALID`，运行时允许再执行一次，并明确要求：
   - 原样复制服务端 GEO 分数；
   - 每个高风险或阻断级无支持/冲突事实必须生成指定 `claim:<claim_key>` 的 `BLOCK`；
   - `decision` 必须与 BLOCK 和告警阈值一致；
   - 只能使用输入已有引用 ID。
10. 第二次质检仍未通过服务端断言时继续失败，不得自动放行或由服务端伪造模型判断。

## 3. 内部契约

新增一个内部 JSON Schema，不新增公开 API：

- `official-site-article-expansion-draft@1`：只含 `blocks[2..5]`；
- 每个块只允许 `paragraph | list`、100–500 字文本和输入范围内的 `citation_ids`；
- 不允许模型在补写阶段返回标题、摘要、FAQ、Schema.org 或其他技术字段。

现有 `official-site-article-draft@1`、`official-site-faq-draft@1`、内容版本、生成运行、质量报告和队列事件保持兼容。

## 4. 持久化与成本

1. 不新增表、迁移、配置项或公开端点。
2. 补写只发生在母稿保存之前；最终一次性保存通过硬门槛的正文，不产生中间内容版本。
3. 每次模型调用继续写入现有 `usage_ledger`，不得隐藏补写或质检重试成本。
4. 官网每日批次的 30 个候选上限、每篇最多重写 3 次和发布重试 3 次均不改变。

## 5. 安全边界

1. 定向补写不得发明价格、地址、电话、资质、客户数量、排名、承诺或超出输入资料的经营事实。
2. 场景后果必须描述真实自动门禁，不使用虚假身份、情绪勒索或伪造指令。
3. 质检语义重试只增强模型遵守既有冻结规则的概率，不降低断言，不把模型漏检结果改写为通过。
4. 两轮补写后仍不足或出现其他问题时，以 `CONTENT_QUALITY_INSUFFICIENT` 失败并进入既有补位流程。

## 6. 明确不做

1. 不把正文硬门槛从 1,300 降到 1,200。
2. 不在服务端拼接模板化灌水文字。
3. 不改变其他六个平台的内容生成流程。
4. 不新增自动放宽质量分、候选上限或发布门禁。
5. 不因本次修复切换模型；官网每日批次继续使用 `CONTENT_MODEL_QUALITY_KEY`，部署默认值仍为 `deepseek-v4-pro`。
