# HOTFIX-20260830-04 抖音登录态顺序轮询与代理超时

## 生产证据与根因

2026-08-30 生产浏览器从 Web 同源地址请求抖音会话时持续收到 HTTP 500 和纯文本
`Internal Server Error`。同一时间窗 Web 容器连续记录：

```text
Failed to proxy http://api:3000/api/v1/platform-accounts/.../douyin-browser-session
Error: socket hang up (ECONNRESET)
```

API 容器在该时间窗保持健康，但没有这些会话请求的完成记录。更早的同一操作日志显示，会话 GET 已分别耗时
4.2、6.8 和 7.2 秒，登录 POST 耗时 12.5 秒，均超过 Web 固定的 3 秒轮询间隔。原实现使用
`setInterval`，上一请求未结束时仍继续发起请求；这些请求在 Worker 的账号锁前排队。Next.js 同源重写代理默认
30 秒超时，而 API 到 Douyin Worker 的默认超时为 65 秒，因此排队请求先被 Web 代理断开，表现为
`ECONNRESET`。前端又静默忽略轮询错误，页面长期保留旧的“等待扫码”状态。

## 修复

1. 抖音登录态改为顺序轮询：请求完成后再等待 3 秒发起下一次，任何时刻最多一个会话轮询。
2. 轮询失败时显示安全的 HTTP 状态提示并继续顺序重试，不再静默保留旧状态。
3. Next.js 同源 API 代理超时调整为 70 秒，略高于 API 到 Douyin Worker 的默认 65 秒上限，使超时由 API 按既有错误契约返回。

## 边界

- 不修改抖音身份验证方式、短信控件选择器或验证码处理。
- 不自动点击短信验证，不改变登录成功判定。
- 不记录验证码、Cookie、手机号、页面正文或凭据。
- 无数据库迁移、公开 API、生产环境变量或发布质量门槛变化。

## 验证

- Web E2E 使用超过轮询间隔的慢响应验证最大并发为 1，并验证 HTTP 500 可见提示。
- 既有二维码替换、短信验证和二次验证持续轮询 E2E。
- Web 类型检查、生产构建、Lint、格式检查和静态发布门禁。
