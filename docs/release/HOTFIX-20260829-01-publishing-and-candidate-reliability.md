# HOTFIX-20260829-01 发布与候选生成可靠性修复

## 根因

1. 浏览器发布 Adapter 的 65 秒等待上限短于真实页面填充、图片上传和发布确认耗时；Publisher 的
   BullMQ 锁和数据库过期租约又只有 120 秒。同一慢任务可能先被上游判超时，再被队列或数据库视为
   失锁，形成状态竞争。
2. 浏览器 Worker 在加载图片和填写编辑器之前就把发布记录改为 `submitting`。浏览器若在点击发布前
   崩溃，系统无法再安全区分“尚未提交”和“远端状态未知”，也没有释放损坏 Context 后的单次恢复。
3. BullMQ 任务耗尽重试或因失锁终止后，只在 Redis 留下 failed job；若数据库任务仍为非终态，缺少
   持久化恢复事件。
4. 企业证照复合声明按整段文本匹配引用，无法接受“同一句包含多个证照、每张证照分别精确映射”的
   合法结构。Quality Checker 还可能引用正文当前位置并不存在的第三方企业名称，形成确定性误报。
5. Content Writer 连续返回非法结构时只在同一模型重试；候选退出日批后只保存通用错误，发布前失败
   页面无法看到生成运行的实际错误和门禁分数差距。

## 修复

1. 百家号、搜狐号和列举网浏览器发布等待上限统一为 300 秒；Publisher 队列锁和数据库过期租约统一
   为 600 秒，默认全局并发收敛为 1。锁、租约和上游等待不再短于浏览器操作窗口。
2. 四个浏览器 Worker 只在发布按钮点击前、保存提交前证据时进入 `submitting`。如果 Playwright 在
   不可逆提交步骤之前明确报告页面、Context 或浏览器崩溃，Worker 释放该账号 Context 并只重试一次；
   `submit` 阶段及点击后的异常仍禁止自动重投。
3. Publisher 执行外部发布时每 60 秒续期数据库租约。BullMQ 任务达到最终失败或 stalled 上限时，按
   原事件 ID 幂等创建新的 Outbox 执行事件；仍在发布中的任务等租约过期后再领取。每个任务最多创建
   3 条队列恢复事件，终态任务不恢复。
4. 企业证照证据允许同一复合声明由多条已授权、持证主体精确一致、证照名称逐项一致的结构化引用共同
   支持。Quality Checker 只移除“报告点名的禁用企业名称在报告位置实际不存在”的误报；正文中确实
   出现第三方企业名称时继续 BLOCK。
5. Content Writer 在同一模型两次结构化输出失败后，使用已配置的质量模型低温重试一次，Schema 不变。
   发布前重写提示现在包含当前分数、最低要求和具体修复动作；日批淘汰项保留对应
   `generation_runs.error_json`，不再只显示通用失败文案。

## 不变边界

- 不修改数据库结构、公开 API、发布幂等键、证照授权边界或任何冻结质量阈值。
- 浏览器网关调用仍在 300 秒窗口内同步等待确定结果。要改为可跨进程重启恢复的真正异步提交，需要
  持久化冻结发布输入并新增状态迁移契约，应另立 ADR，不能在维护修复中静默改变。
- 不增加“连续 3 个相似候选失败后停止补位”的硬熔断。ADR-0023 要求在每日候选上限内持续补位；
  本次通过模型兜底和可操作诊断减少重复浪费，候选上限和补位语义保持不变。
- 不自动重跑旧候选、旧质量报告、旧发布任务或生产失败记录。
