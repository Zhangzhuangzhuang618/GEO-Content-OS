# HOTFIX-20260829-05 抖音接收短信方式选择顺序

## 生产证据与根因

2026-08-29 生产诊断同时记录到“接收短信验证码”“发送短信验证”和“手机刷脸验证”可见，验证码输入框可见但不可操作，且前景层没有 `#uc-second-verify` 或 `role=dialog`。Worker 因此先命中页面底层的旧验证码输入框，并在选择“接收短信验证码”之前按遮挡失败，实际没有向抖音发起短信请求。

## 修复

1. 保留 `#uc-second-verify` 和带验证标记的标准对话框优先级；两者不存在时，从“身份验证”“短信验证码”“接收短信验证码”和原设备扫码等可见锚点向上查找同时包含至少两项验证证据的最小容器。
2. 短信继续操作时，只要前景容器内存在唯一可见的“接收短信验证码”，先精确点击该方式，再重新定位验证码输入框和发送控件；底层可见但不可操作的旧输入框不再提前终止流程。
3. 只有找不到接收短信方式且验证码输入框仍被遮挡时，才返回 `CAPTCHA_REQUIRED`。语义不同的“发送短信验证”和刷脸验证仍不自动操作。
4. 无标准对话框的前景容器会加入仅供本次页面诊断截图标边的临时属性；截图脱敏范围和日志白名单保持不变。

## 边界

- 短信发送仍必须由用户在 GEO Content OS 明确点击触发。
- 不读取、识别、破解或绕过抖音验证码与风控，不记录验证码、手机号正文、Cookie 或原始 DOM。
- 无数据库迁移、公开 API、生产配置、质量门槛或登录成功判定变化。

## 验证

- Playwright 回归场景模拟无 `role=dialog` 的三方式选择浮层及其下方被遮挡的旧验证码输入框，验证前景容器被识别、只选择“接收短信验证码”，并进入可操作的验证码输入阶段。
- 既有标准验证层、输入框安全遮罩、短信重发、原设备二维码和登录完成场景继续通过。
- Worker 单元测试、完整浏览器集成测试、类型检查和构建通过；相关 API/Web 测试、Web 生产构建和发布静态门禁通过。
