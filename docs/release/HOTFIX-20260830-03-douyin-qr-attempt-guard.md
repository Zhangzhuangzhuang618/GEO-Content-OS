# HOTFIX-20260830-03 抖音二维码尝试保护与日志去重

## 已确认的生产证据

2026-08-30 生产 Worker 在同一会话连续记录三次二维码登录结束后的
`Douyin browser login requires additional verification`，但只保存一份当前尝试诊断。代码路径表明，每次日志都来自一个独立的异步二维码尝试；旧尝试在核对当前会话之前已经打印日志。

同一时间窗没有出现 HOTFIX-20260830-02 新增的
`Douyin login verification action requested`。诊断仍为 `challenge_type=identity_choice`、
`available_methods=[sms_code]`、`has_code_input=false`。这只能证明页面停在验证方式选择阶段，不能证明短信输入框被风控阻断，也不能证明短信发送动作到达了 API 或 Worker。

## 根因与修复

1. Web 在二维码已经生成的 `qr_ready` 阶段仍展示普通生成入口，允许用户在上一尝试尚未结束时再次启动二维码流程。
2. `qr_ready` 阶段现在隐藏普通入口；替换当前二维码必须使用独立按钮并确认。页面刷新后无法恢复二维码图片时，也通过同一显式路径重新生成。
3. Worker 在异步二维码失败后，先核对会话状态、版本和过期时间。已被新二维码替代的旧尝试不再打印二次验证或失败日志，也不保存诊断。

## 未做的推测性修改

- 不自动点击短信验证，不修改抖音页面选择器。
- 不把 `identity_choice` 阶段没有输入框解释为短信失败。
- 若要继续定位短信动作未执行，需要同一操作时间窗的 API 请求状态、Worker 动作日志，以及用户点击“发送短信验证码”后的 GEO 页面状态。

## 安全与兼容边界

- 短信发送、重发和验证码提交仍必须由用户明确触发。
- 验证码、手机号、页面正文、原始 DOM 和凭据不进入日志。
- 无数据库迁移、公开 API、生产配置、登录成功判定或发布质量门槛变化。

## 验证

- Web E2E：活动二维码不能被普通按钮替换，取消确认不发请求，确认后只发一次新请求。
- Worker 单元测试：陈旧二维码尝试不写状态、不保存诊断、不打印结果日志。
- Web 类型检查与生产构建、Worker 类型检查与测试、静态发布门禁。
