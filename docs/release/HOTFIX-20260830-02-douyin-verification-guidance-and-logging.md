# HOTFIX-20260830-02 抖音二次验证引导与日志语义

## 生产证据与根因

2026-08-30 生产日志连续记录三次二维码登录结束后的 `CAPTCHA_REQUIRED`，两份诊断均为
`challenge_type=identity_choice`、`available_methods=[sms_code]`、`has_code_input=false`，页面签名相同。
身份验证方式选择页尚未进入短信验证码输入步骤，因此此时没有输入框是正常状态，不足以证明抖音风控阻断了
短信输入。日志中也没有验证动作到达 Worker 的证据；连续三次异步二维码结束记录说明登录流程被重复启动。

Web 在 `attention_required` 阶段仍突出显示“生成登录二维码”，使操作人员容易重复扫码并放弃当前二次验证
进度；Worker 又把预期的二次验证转换记录为“登录验证失败”，进一步放大了误判。

## 修复

1. Web 在二次验证阶段隐藏普通二维码入口，明确说明扫码授权已完成、身份方式尚待选择。
2. 重新扫码改为“放弃当前验证并重新扫码”，执行前必须由用户确认。
3. Worker 将 `CAPTCHA_REQUIRED` 和 `PAGE_SIGNATURE_CHANGED` 记录为“需要额外验证”，其他异常仍记录为失败。
4. Worker 在接受二次验证操作后记录动作类型，使日志可以确认短信发送、重发或校验请求是否实际到达。

## 安全边界

- 短信发送、重发和验证码提交仍必须由用户明确触发。
- 日志只记录账号 ID、错误码和动作枚举，不记录验证码、手机号、页面正文、原始 DOM 或凭据。
- 不自动选择验证方式，不绕过抖音安全验证，不放宽登录成功判定。
- 无数据库迁移、公开 API、生产配置或发布质量门槛变化。

## 验证

- Web 二次验证交互 E2E：普通二维码入口隐藏、放弃操作需确认、短信动作保持显式。
- Douyin Browser Worker 单元测试：预期挑战日志语义、动作日志脱敏和异常失败分支。
- Web 类型检查与生产构建、Worker 类型检查与测试、静态发布门禁。
