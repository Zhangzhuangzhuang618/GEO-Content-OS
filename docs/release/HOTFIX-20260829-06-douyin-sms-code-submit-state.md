# HOTFIX-20260829-06 抖音短信验证码提交状态

## 生产证据与根因

2026-08-29 生产操作已成功触发抖音短信，页面诊断同时记录到验证码输入框可见、脱敏接收号码已出现，但 `code_input_actionable=false`。Worker 将输入框中心点的试点击结果直接用作 `has_code_input`，局部浮层拦截鼠标点击时便误判整个短信步骤不可用，Web 因 `has_code_input=false` 隐藏了已实现的验证码输入和提交区。

## 修复

1. 短信步骤以“输入框可见、启用、可编辑”为基础；输入框自身可点击，或同一前景验证层的唯一提交控件可点击，任一条件成立即识别为可提交的验证码步骤。
2. “接收短信验证码”本身已发送短信、且页面直接进入输入阶段时，不再强制要求页面另有“发送/获取验证码”控件。
3. 提交验证码前先校验“验证/确定/提交”控件实际可点击，通过后才填入验证码；不使用强制填写或强制点击。
4. 现有 Web 交互和 API 契约不变；Worker 正确上报 `has_code_input=true` 后，Web 自动显示“短信验证码”、“提交验证码”和重发状态。

## 安全边界

- 短信发送、重发和提交仍必须由用户在 GEO Content OS 明确触发。
- 验证码不落库、不写日志、不进入诊断截图。
- 提交控件被安全遮罩拦截时继续失败关闭，不识别、破解或绕过抖音验证。
- 无数据库迁移、公开 API、生产配置或发布质量门槛变化。

## 验证

- Playwright 新增“输入框局部点击目标被覆盖，但同层提交控件可用”场景，验证短信步骤被识别、验证码可提交并完成登录。
- 既有身份方式选择、无标准对话框、全屏安全遮罩、短信重发和原设备二维码场景继续通过。
