# HOTFIX-20260907-03 资料 JPEG 尾部附加数据兼容

用户授权：修复营业执照上传失败并部署生产。属于 T155 / ADR-0053 的上传校验 Bugfix。

## 证据与修复

- 生产上传返回 HTTP 422，未创建资料或解析任务。本地同名 JPG 为 257894 字节、1807×1279，
  可完整解码，但 JPEG EOI 标记后有 24 字节附加数据；生产校验错误地要求 EOI 必须在文件末尾。
- JPEG 保留扩展名、MIME、SOI 和 EOI 校验，允许结束标记后的附加数据。
- 所有资料图片在既有大小、尺寸和像素上限检查后完整解码；不能只读头部元数据放行截断像素数据。
  解码告警或错误均拒绝；使用 stats 避免保留整张 raw 输出缓冲，不改写原图、文件哈希或私有存储内容。
- 继续使用原有安全扫描、企业字段、有效期、主体隔离及公开授权规则。不自动重试上传、生成或发布。
- 无数据库迁移、公开 API、Web 或生产配置变更，仅构建和替换 API 服务。

## 验证

- 先运行回归测试复现旧行为：带 24 字节/换行尾部的合法 JPEG 被拒绝；带 EOI 的截断图片被错误接受。
- 修复后真实 Fastify multipart 解析测试 9 项通过，验证证照字段覆盖全局 multipart 限制、原图哈希
  保留、合法尾部、MIME/扩展名错配、伪造签名、缺少 EOI 和截断图片。
- 上传集成测试 20 项通过（独立 PostgreSQL / MinIO），包含普通/带尾部证照、私有对象与入库事务。
- API 知识和安全测试合计 44 项（含上述 9 项），图片 Adapter 测试 23 项通过。
- API 生产构建、API 源码/图片类型检查及修改文件 ESLint 通过。
- 全量 API 测试类型检查仍有 6 处既有错误：`test/e2e/system/runtime.d.mts` 的 `PublishClaim`
  声明缺少 `accountId`，而 `system.spec.ts` 使用该字段；两文件均与部署前基线相同，本次不顺带修改。
- 用户本地同名 JPG 只读验证完整解码通过；原文件未修改，也未作为测试 fixture 提交。

## 部署与回滚

- 部署前核对本地、远端与生产仓库基线 fe19e34；16 个服务健康、API readiness HTTP 200。
- 使用当前提交的干净归档构建，保留服务器原有环境改动与所有数据卷。
- 替换前为旧 API 镜像添加唯一回滚标签；只执行 API 的 no-deps 更新，不重建 Worker 或浏览器。
- 部署后在实际运行容器中核验代码、合成 JPEG 正反例、API readiness 和服务日志。
- 回滚仅将保留的 API 镜像恢复为服务镜像并重建 API，无数据库回退。
