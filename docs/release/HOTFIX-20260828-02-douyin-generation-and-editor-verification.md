# HOTFIX-20260828-02 抖音生成与编辑器校验修复

## 问题

- 抖音平台规则可能被后续通用 few-shot 示例稀释，模型返回旧式或不完整的 `platform_meta`，直到较晚的
  编辑质量门禁才失败。
- 抖音首稿未通过既有叙事门禁时，原流程最多只有一次完整修订，对结构性问题的稳定修复空间不足。
- 创作者中心可能在主文案换行附近插入零宽分隔符。页面可见文本与待发布文本一致，但 Worker 的逐字比较
  会把不可见字符判为篡改并停止自动提交。

## 修复

1. 抖音生成不再注入会与图文结构冲突的通用 few-shot；当前抖音规则紧邻最终输入，优先级明确。
2. Content Writer 输出契约直接约束抖音 `image_note` 的标题、正文块、420–900 字主文案、3–8 个话题和
   6–9 张图文卡片，旧式元数据在进入编辑质量门禁前即失败。
3. 抖音首稿未通过现有确定性质量检查时，最多执行 3 次含首稿的质量报告驱动生成；每轮仍由模型返回完整
   内容并重新经过同一门禁，全部不通过则失败关闭。
4. Browser Worker 在提交前比较主文案时仅忽略空白和平台插入的零宽分隔符；其他可见字符仍须一致，
   不改变实际填写、提交或成功判定。

## 边界

- 不降低事实、品牌、资质、图片或抖音图文冻结质量门槛，不由服务端修改正文或伪造质量结论。
- 不自动重新生成、重评或发布旧内容、旧质量报告和旧任务。
- 无数据库迁移、公开 API 或生产配置变化；本 Hotfix 不部署生产环境。

## 验证

- Contracts、Content Writer 与 AI Worker 回归覆盖抖音严格输出结构、专用 Prompt 顺序及第三轮修复成功。
- Browser Worker 本地仿真覆盖编辑器插入零宽分隔符后仍可通过可见文本一致性检查。
- 受控真实发布完成：`工厂搬迁前怎么核对设备通道` 在抖音内容管理中显示已发布，外部作品 ID 为
  `7678865658255248682`；Worker 只读对账返回同一 ID，系统任务随后通过既有人工未知结果处置闭环完成，
  未触发重复发布。
