# HOTFIX-20260830-10 抖音日批字段长度定点修复

## 根因

HOTFIX-20260830-09 虽然把抖音日批拆成了浅层草稿，但浅层 JSON Schema 仍把标题、叙事段落和卡片文字
的发布下限写成 `minLength`。生产 18 个候选中 15 个首稿直接以 `SKILL_OUTPUT_INVALID` 失败；错误路径
集中在方案段落、费用、防护、工期、清单、结论和卡片正文长度。结构校验先于确定性内容验收，因此这些
可定位的短字段没有进入 Flash 定点修复，直接升级到 Pro，违背了 Flash-first 的调用顺序。

生产另有一个候选显示两份 `decision=pass`、100 分报告后仍进入重写。只读核验确认其两次
`automation_gate_json.passed=false`：证据分 55 低于 90，总分 83.6 低于 85。报告决策与自动化冻结门禁
是两层结论，进入重写是正确行为，不是状态判断错误。

## 修复

1. 抖音浅层草稿 Schema 只验证字段、类型、数组形状和最大长度，不再把内容下限当作结构有效性。
2. 首稿提示明确每个叙事和卡片字段的生产长度范围，优先提高首次 Flash 输出质量。
3. 原有最小长度转为服务端确定性问题，并携带准确的 `repair_target`；Flash 只修改不达标字段。
4. 短字段导致的冻结 Schema、主文案总长度和卡片形状问题在本轮先去重，避免一次短字段扩大成全稿或
   全卡片重写。
5. 定点修复后重新执行 ADR-0074 编辑门禁、企业名称、资质证据和冻结 Content Writer Schema；仍不
   合格时才调用 Pro。所有原有最小值、最大值和发布阈值保持不变。
6. 自动化仍以 `automation_gate_json.passed` 决定排期或重写；不得使用质量报告的
   `decision=pass` 绕过分项阈值。

## 部署与回滚

- 无数据库迁移、公开 API、新环境变量或 Compose 变化。
- 仅需重建并替换 `ai-worker`；历史批次不会自动重跑。
- 部署后由发布管理员显式重新发起抖音日批，并核对 Flash 首稿、Flash 定点修复、Pro 兜底三类实际
  调用数量及最终质量门禁结果。
- 回滚到上一提交并重建 `ai-worker` 后恢复原浅层 Schema 行为。
