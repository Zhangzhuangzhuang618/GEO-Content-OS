# HOTFIX-20260822-03 百家号扫码登录运行时恢复

## 问题

- 百家号登录页二维码已经加载完成后，Worker 仍使用 Locator 截图；Playwright 会额外等待字体和元素稳定，生产上出现约 28 秒超时。
- 登录页发生 `Page crashed` 或上下文关闭时，本次扫码直接失败，用户只能再次手工点击。
- Worker 的 `BROWSER_GATEWAY_UNAVAILABLE`（503）被 API 统一包装为状态冲突（409）；Web 代理连接中断时又只显示通用 500，用户无法区分状态冲突和临时运行时故障。

## 修复

- 二维码完成加载后读取其当前资源地址。生产 PNG 响应通过浏览器上下文携带 Cookie 直接取得并校验 PNG 签名，不再触发页面截图等待；同源 SVG 等仿真资源使用画布转换为 PNG。
- 扫码启动首次遇到 Playwright 页面崩溃或页面、上下文、浏览器已关闭时，释放该账号上下文并自动重试一次。第二次仍失败则保持失败关闭，不无限重试。
- Contracts 增加 `BROWSER_GATEWAY_UNAVAILABLE`（HTTP 503），API 保留 Worker 的脱敏原因，Web 对结构化 503 和代理 5xx 显示明确的稍后重试提示。

## 不变边界

- 不保存或记录二维码、Cookie、账号密码、令牌或浏览器 storage state 明文。
- 不把验证码、页面签名变化或登录失效伪装为临时故障；这些错误不参与自动重试。
- 不修改内容质量门槛、发布重试上限、发布状态机、未知态防重复规则、旧任务或旧质量报告。
- 无数据库迁移，不自动操作生产百家号。

## 验证

- 百家号 Worker 单元测试覆盖页面崩溃后释放并单次重试。
- 本地 Chromium 仿真验证二维码输出为真实 PNG，并通过既有登录、发布、回执和对账 13 项回归。
- Contracts、API 错误映射和 Web 错误提示均有回归测试。
- 通过 Worker、API、Web、Contracts 类型检查和生产构建后方可提交。

## 部署

- 重新构建并部署 `api`、`web` 和 `baijiahao-browser`；Contracts 由 API 构建依赖带入。
- 无需执行数据库迁移。
- 部署后重新点击“扫码登录”；旧失败发布任务不会自动重投。
