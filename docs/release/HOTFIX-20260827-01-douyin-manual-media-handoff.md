# HOTFIX-20260827-01 抖音手动发布配图衔接

## 现场证据

- 新生成的抖音图文已通过冻结质检，内容版本包含 8 张结构化卡片。
- 从内容页直接创建手动发布任务后，没有创建 `content_media_runs`，也没有生成
  `content_media_assets`。
- Publisher 先把任务置为发布中并消耗一次尝试，随后 Render 因“卡片 8 张、合格图片 0 张”返回
  `CARD_ASSET_COUNT_MISMATCH`；外部抖音页面尚未提交任何作品。

## 修复

1. 手动创建或重试发布任务时，仅对抖音 `image_note` 自动创建幂等媒体运行；旧抖音口播脚本和其他
   平台保持原流程。
2. Publisher 在领取抖音图文任务前核对“卡片数 = 通过媒体门禁的图片数”。图片未齐时保持任务为
   `scheduled`，不增加发布次数、不进入平台 Render，也不调用外部发布。
3. 抖音卡片媒体完整落库后，Media Worker 为同一发布任务写入新的执行事件；事件沿用任务版本和排期
   时间，避免初始发布事件与配图事件之间的竞态。
4. 媒体状态只有在抖音卡片与合格图片数量完全一致时才显示为“已就绪”；部分素材不再误报就绪。

## 不变边界

- 不降低内容、事实、品牌、资质、图片或平台冻结门禁，不由服务端伪造质量通过。
- 不自动重写或重新评估旧内容和旧质量报告。
- 不自动重投未知外部状态；本次失败发生在外部提交前，修复部署后仍通过原任务的显式重试入口恢复。
- 无数据库迁移、公开 API 或生产配置变更。

## 验证

- API 测试覆盖手动创建和失败重试均触发必需媒体检查。
- Publisher PostgreSQL 集成测试覆盖素材未齐时任务保持排期且尝试次数不增加。
- Media Worker 测试覆盖素材完成后续接同一任务的执行事件。
- API、AI Worker、Publisher 定向测试、类型检查和构建通过。
- 使用仓库要求的 Node.js 22 执行 `pnpm verify`，完整门禁通过；集成测试共 56 个文件、
  289 项通过。
- `pnpm release:check` 的静态检查仍因 T158 已存在的 `PROJECT_CONTEXT.md` 文案与旧检查器
  固定字符串不一致而失败（检查器要求“冻结表数：57”，现文档写“冻结基线表数为 57”）；本
  Hotfix 不修改该无关冻结基线。
